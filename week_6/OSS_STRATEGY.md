# 🌐 [6주차 선택과제] OSS 라이선스 분석 및 Inner Source 도입 로드맵
 💡 **안내:** 본 문서는 생성형 AI의 도움을 받아 작성되었습니다.

## 1. 주요 OSS 라이선스 비교 분석
사하구청 AI 상담사 프로젝트의 공개 및 확장을 위해 대표적인 오픈소스 라이선스 3가지를 비교 분석했습니다.

| 구분 | MIT License | Apache 2.0 | GNU GPL v3 |
| :--- | :--- | :--- | :--- |
| **성격** | 아주 관대함 (자유로움) | 관대함 (특허 조항 포함) | 엄격함 (전염성 있음) |
| **상업적 이용** | 가능 | 가능 | 가능 |
| **소스코드 공개 의무** | 없음 | 없음 | **있음 (파생 저작물 포함)** |
| **선택 기준(채택)** | **✅ 채택:** 공공(사하구청) 목적의 프로토타입이며, 많은 사람의 자유로운 활용과 기여를 유도하기 위해 가장 제약이 적은 MIT 라이선스를 선택함. | 도입 고려 안 함 | 코드를 가져다 쓴 기업도 무조건 코드를 공개해야 하므로, 기업의 참여를 꺼리게 만들 수 있어 배제함. |

## 2. 조직 내부 적용을 위한 Inner Source 도입 로드맵
외부 오픈소스 문화를 사하구청(또는 사내 개발팀) 내부 조직에 도입하여 협업 효율을 높이는 '이너소스(Inner Source)' 구축 로드맵입니다.

### 🚩 Phase 1: 문화 조성 및 인프라 구축 (1~3개월)
- **표준화:** 전사 공통 GitHub/GitLab 플랫폼 구축 및 권한 개방 (모든 팀의 코드를 읽기 권한으로 사내 공개)
- **문서화:** 사내 기여 가이드(`CONTRIBUTING.md`) 및 코드 리뷰 템플릿 표준화
- **교육:** 폐쇄적인 개발 문화 타파를 위한 "Inner Source 101" 사내 세미나 개최

### 🚩 Phase 2: 시범 프로젝트 운영 (4~6개월)
- **Trusted Committer(관리자) 선정:** 공통 UI 컴포넌트나 공통 API 모듈 등을 시범 이너소스 프로젝트로 선정하고 전담 리뷰어 배정
- **크로스 팀 PR:** A팀 개발자가 B팀의 코드에 자유롭게 Pull Request를 날리고 리뷰를 주고받는 경험 축적

### 🚩 Phase 3: 평가 보상 및 전사 확산 (7개월 이후)
- **보상 체계:** 타 팀 프로젝트에 유의미한 PR 기여를 많이 한 개발자에게 인사 평가 가산점 및 사내 포상 지급 (Gamification)
- **사일로(Silo) 파괴:** 중복 개발 방지 및 사내 기술 스택의 자연스러운 통일 달성
